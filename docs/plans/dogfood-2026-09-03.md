## 11. Friction log

Severity: **High** = blocks or silently corrupts the scientific record · **Medium** = costs
real time or trust · **Low** = polish.

Findings were captured against the tree as it stood during the session (`b0d7a7d` plus
whatever parallel agents had landed at each moment). One item — F3 — was fixed by a parallel
agent while the session was running and is annotated as such; every other item was
re-checked against the working tree before this report was written and is still open.

### F1 · High · arXiv adapter phrase-wraps every query; zero results are recorded as a completed search

```
$ research discover "pre-trained transformer encrypted traffic classification" --source arxiv --max-pages 1
SR0002  0 candidate(s) …  cursor arxiv  1 page(s), exhausted    failures: []
```

`providers/search/arxiv.py::_search_query` builds `all:"<the entire query>"`. Live check:
`all:"encrypted traffic classification"` → 10 entries; `all:"pre-trained transformer
encrypted traffic classification"` → 0; `all:"LLM network intrusion detection"` → 0.
Any research question longer than three or four words returns nothing, and the SearchRun
records `exhausted: true` with an empty `failures` list — indistinguishable from a genuine
empty result, which §42 F says must never happen.

**Proposed decision:** build a conjunction (`all:"term" AND all:"term"`) rather than one
phrase; if a phrase query yields 0, retry unquoted and record which form produced the page.
Persist a `zero_result_phrase_query` run note so coverage can discount it.

### F2 · High · `research coverage` never writes its funnel to the Claim, so no claim can exceed L1

```
$ research coverage C0003 --universe "…" --cutoff 2025-08 --source arxiv --source openalex
  funnel   discovered 515 -> screened 8 -> relevant 5 -> full_text_available 5 -> examined 5
$ research claim audit C0003
  coverage: 0 of 0 relevant works examined, 0 unresolved; estimated overturn risk unknown
  reasons: - L2 corpus_pattern: the coverage record names no relevant works, so there is no corpus to generalize over
```

`claims/C0003.yaml` → `coverage: {relevant_works: 0, examined_works: 0, search_runs: [], cutoff: null}`.
Two commands compute the same quantity and disagree; the one the audit reads is always
zero. Every literature-wide claim is capped at L1 for a plumbing reason.

**Proposed decision:** make one of them authoritative. Either `coverage` persists a
`ClaimCoverage` onto the claim (and `claim audit` refuses to run without one), or
`claim audit` recomputes the funnel from the SearchRuns itself and `coverage` becomes a
read-only view of it.

### F3 · High · the `structured-traffic` plugin's interrogation schema is unreachable from the CLI — **fixed mid-session by parallel work**

```
$ research interrogate W0001 --schema plugin:structured-traffic …
error: unknown interrogation schema 'plugin:structured-traffic'; known: generic-empirical
$ research interrogate W0001 --schema plugins/structured-traffic/interrogation/paper.yaml …
error: cannot read interrogation schema …: Invalid JSON: expected value at line 1 column 1
```

`cli/commands/evidence.py::SCHEMAS` contains only `DEFAULT_SCHEMA`; `_schema()` parses JSON
only; nothing in `cli/` or `workspace/` ever calls `plugins.load_plugin`. The runtime
exists and works — `load_plugin(...).interrogation_schemas["structured-traffic:paper"]`
returns all 27 merged fields — it is simply not wired to a transport. Task 15.1's entire
deliverable requires the researcher to write Python.

**Proposed decision:** a `plugins:` list in `research.yaml`, loaded once in `context_for`,
registering each plugin's schemas under `<plugin>:<schema_name>`; `--schema` accepts YAML
as well as JSON; `research capabilities` (or a new `research plugins`) lists what loaded.

**Status:** resolved during this session by concurrent work — `src/research_harness/cli/plugins.py`
landed while the dogfood was running, and re-running
`research interrogate W0001 --schema plugin:structured-traffic --field traffic.traffic_unit`
afterwards resolved the schema correctly. Recorded here because it was a real blocker for
most of the session and because it is the specific gap Gate P15 is meant to expose: the
plugin, the SPI and the contract tests were all green in Phase 15.1 while the vocabulary
remained unreachable from every transport. **Design decision worth keeping:** a plugin
contribution is not "done" until a transport can reach it, and a contract test that only
exercises `load_plugin` cannot show that.

### F4 · High · false `citation_mismatch` errors from arXiv-id extraction and a strict year filter

```
[ERROR] citation_mismatch: main.tex:8: citation 'meng2023netgpt' cannot be traced to a corpus work
```
…for NetGPT, which is W0002. Two compounding causes:

```python
>>> arxiv_base_id('arXiv preprint arXiv:2304.09513')
'arxiv preprint arxiv:2304.09513'      # expected '2304.09513'
```

`manuscript/support.py::_entry_arxiv` falls back to scanning `url`/`note`/`journal` for
"arxiv" and hands the whole field to `arxiv_base_id`, which lowercases rather than extracts —
so the fallback yields a key that can never match. The title fallback then applies a strict
year filter, and W0002's ingested year is **2025** (taken from the arXiv v3 banner) while the
bibliography correctly says 2023, so the exact title match is discarded too. Adding
`eprint = {2304.09513}` cleared all three errors.

**Proposed decision:** (a) regex-extract the id inside `arxiv_base_id`; (b) when the
normalised title matches exactly, treat a year mismatch as a tiebreaker warning rather than
a disqualifier; (c) have `acquire` reconcile the Work's year against the discovery
candidate's metadata (see F5).

### F5 · High · discovery finds better metadata than the corpus holds and silently discards it

The OpenAlex candidate for ET-BERT carried the correct six authors
(`Xinjie Lin, Gang Xiong, Gaopeng Gou, Zhen Li, Junzheng Shi, Jing Yu`) and venue
(`Proceedings of the ACM Web Conference 2022`). It resolved `same_work → W0001`. W0001's
`work.yaml` still reads:

```yaml
authors:
- anced traffic data for accurate classification
- which is challenging
- "ORVH\x10GRPDLQ"
```

The harness knew the right answer and threw it away. The same class of loss gives W0002 the
wrong year, which is half of F4.

**Proposed decision:** on a `same_work` resolution where the candidate's metadata differs
from the Work's, stage a metadata-reconciliation item into the review inbox (origin
`external_metadata`, Tier 1) instead of dropping it. Never overwrite silently — but never
discard silently either.

### F6 · Medium-High · parse diagnostics are recorded and never shown

```
$ research parse W0001
W0001 / A0001-1: parsed 304 blocks across 11 pages
  parser  pymupdf@1.1
```

The actual diagnostics — `undecodable:14; shift:29; pages:1,4,8,11` — live only in each

### F7 · Medium-High · "conflict" fires on any field with more than one answer

18 of 39 review items were conflicts; **2 were real**. The rest read:

```
cand_67e625b05256f93d  conflict  tier 2  traffic.author_stated_limitations  supported
    Generalizability: The variability of encrypted traffic due to changes in the content of…
    - 1 competing candidate(s) propose a different value for field 'traffic.author_stated_limitations'
```

Two distinct limitations stated by the same paper are not competing values. The plugin
already declares which fields are multi-valued (`multi_label: true` in
`schemas/traffic.yaml`); the conflict detector does not read it.

**Proposed decision:** raise `conflict` only for single-valued fields, or where two
candidates quote overlapping spans with different numerics/labels; route additional answers
to a multi-valued field to `routine`. Conflict-first review is worthless if the queue is
89% noise.

### F8 · Medium · `research inbox` shows 20 of N without saying so

Header reads `39 item(s) to review`; exactly 20 print. The `--limit 20` default appears only
in `--help`, and the JSON payload quietly carries `count: 39, len(items): 20`. A researcher
who works the list top to bottom will believe they cleared the queue.

**Proposed decision:** `showing 20 of 39 — use --limit 0 for all`.

### F9 · Medium · screening records why a paper was excluded but not why it was included

```
$ research screen SR0001 doi:… --include --exclude "reason"
error: screen needs exactly one of --include, --exclude "reason", or --screened
```

`--exclude` requires a reason; `--include` accepts none. PRISMA-style provenance (§18)
needs both halves, and inclusion is the decision a reviewer is most often asked to defend.

**Proposed decision:** `--include [REASON]`, stored in the same field as the exclusion
reason with the decision recorded separately.

### F10 · Medium · snowball reference segmentation manufactures hundreds of junk seeds

`research snowball W0001 --depth 1` turned 45 references into **474 candidates**
(`searches/SR0004.yaml`, 1 MB). Representative "works" it resolved as `distinct_work`:

```
title:but cannot fly in the annual meeting of the association for computational linguistics 7811 7818
title:international conference on learning representations
title:the international conference on neural information processing systems 6000 6010
```

These are fragments of references split across blocks. They flow straight into the coverage
denominator: C0003's funnel begins `discovered 515`, and most of that is artefact.

**Proposed decision:** require a reference block to look like a complete reference (author
+ year + venue, or a resolvable identifier) before it becomes a seed; record the remainder
as `unresolved_keys` on the run so the funnel stays honest. Consider joining consecutive
`reference` blocks that lack a leading `[n]` marker.

### F11 · Medium · `review candidate --help` documents a refusal that does not exist

> Acceptance is refused for any actor that is not the researcher, and for an interpretive
> or Tier-2 candidate under every policy — that is the review gate, not a preference.

```
$ research review candidate cand_3a27e061705f6ff3 --accept    # traffic.representation_family, risk 2
cand_3a27e061705f6ff3: accept -> E0002
```

The Tier-2 rule belongs to `review batch`. As written, the most load-bearing sentence in the
review UX is false, and a researcher reading it would believe a gate is protecting them that
is not.

**Proposed decision:** correct the docstring; say plainly that `review candidate` is the
human gate and accepts any tier, and that `review batch` is the one with conditions.

### F12 · Medium · reviewing an item takes two commands and the review command shows no source

`research review candidate <id>` prints nothing about the span it is about to canonise. The
context is in `research inbox --json` under `source_context` — capped at 20 items (F8) and
formatted for machines. Honest rejection means keeping a JSON blob open in another window.

**Proposed decision:** `research review candidate <id>` with no action flag prints the item,
its verdict, its discrepancies and its source context; add `research review next` to walk
the queue in §24.2 order.

### F13 · Medium · a categorical answer carries no category

`EvidenceCandidateOutput` has `field` and `exact_text` but no label field, so an answer to
`traffic.representation_family` (categories `raw sequential | field-based | behavior-aware |
unclear`) is only a quoted span. The label is re-derived much later by keyword
`ClassificationRule`s at matrix-build time, which means the plugin's `traffic_unit` and
`dataset_age` validators — whose whole job is taxonomy membership — have nothing to run
against, and the classification is only as good as a substring match.

Observed cost: my first rule set labelled RAPIER `raw sequential` because its
behaviour-vector sentence contains "raw encrypted network traffic".

**Proposed decision:** add an optional `labels: list[str]` to `EvidenceCandidateOutput`,
validated against the field's declared `categories` and staged for review like everything
else. Keep matrix rules as the reproducible cross-check, not the sole source of truth.

### F14 · Medium · the plugin schema forbids the evidence types its own questions invite

```
rejected  traffic.traffic_unit: evidence type 'definition' is not allowed for field
          'traffic.traffic_unit' (allowed: method_description, representation_description)
rejected  traffic.author_stated_limitations: evidence type 'deployment_assumption' is not allowed
```

The single best span in ET-BERT for "which unit is one sample" is a definition sentence
("A BURST is defined as a set of timeadjacent network packets…") and it was refused. Correct
enforcement of a wrong declaration.

**Proposed decision:** add `definition` to `traffic.traffic_unit` and
`deployment_assumption` to `traffic.author_stated_limitations` in
`plugins/structured-traffic/interrogation/paper.yaml`.

### F15 · Medium · the claim auditor's proposed wording is computed and discarded

The scripted auditor returned
`"Among the pre-trained transformer systems examined here, tokenisation schemes differ
(bi-gram over raw datagrams, WordPiece over hex, header-field text), and no two share a
vocabulary."` — the sentence a writer actually wants. `claim audit` printed the
deterministic `among the papers examined` and `claim show C0001` retains no trace of it.
`ClaimAuditOutput.maximum_defensible_wording` is a required field with nowhere to go.

**Proposed decision:** print it as *auditor proposed wording* beside the deterministic
ceiling and persist it on the assessment. The model may not raise the ceiling; it can still
phrase what sits under it.

### F16 · Low · `matrix build --matrix S0001` overwrites without showing the diff

Rebuilding S0001 after a rule fix moved W0004 from `raw sequential, behavior-aware` to
`behavior-aware` and printed only `classified 5 of 5`. `MatrixCellChange` with
`added_labels`/`removed_labels` already exists in `synthesis/matrix.py` and is not used by
the CLI.

**Proposed decision:** print the cell diff on rebuild, and refuse silently overwriting a
matrix that has dependent Claims without `--force`.

### F17 · Low · `research egress` is silent about model providers when none are configured

The report lists 3 embedding and 5 search providers and says nothing about model egress —
the largest channel — because `providers:` is empty. A researcher checking what leaves the
workstation before a run reads a complete-looking table.

**Proposed decision:** always print a model-provider section, with an explicit
`(none configured — model stages will refuse)` row.

### F18 · Low · one malformed candidate discards the whole field's extraction output

`ExtractionOutput` validates all-or-nothing per (field, chunk). A wrong `rationale` shape in
one candidate produced
`rejected traffic.dataset: … 3 validation errors for ExtractionOutput` and lost the two
valid candidates alongside it. With a real model this is a routine occurrence and an
expensive one.

**Proposed decision:** validate candidates individually and record per-candidate rejections,
keeping the survivors — the module already has a `RejectedOutput` type for exactly this.

### F19 · Low · no way to name a set of fields

Eight `--field` flags per invocation, no `--fields a,b,c`, no "all fields except". Quoting
them as one string fails with `No such option:` and the whole flag list echoed back.

### F20 · Low · ~1 s CLI startup dominates any loop

`uv run research --version` → 0.97 s. The 39-item review loop spent roughly 80 of 90 seconds
importing. `research serve` exists as a workaround, but the documented path is the CLI.

**Proposed decision:** measure and trim import cost (lazy provider/adapter imports), or ship
a `research shell` that keeps the workspace open across commands.

### F1 · arXiv phrase-wrapping, and zero results that looked complete

`arxiv.search_query_for` now sends one `all:"term"` clause per term, AND-ed together, so
`pre-trained transformer encrypted traffic classification` goes out as five clauses instead
of one unmatchable phrase. A double-quoted substring of the researcher's text stays one
phrase clause, which is how a phrase can still be asked for deliberately;
`providers.search.base.query_terms` is the shared, order-preserving tokenizer.
`submittedDate` bounds are unchanged and still AND-ed on.

The second half — the silent zero — is fixed separately, because it is the part that
corrupts coverage. A zero-result page for a query of more than one term now carries a
`zero_result_query:` warning naming **exactly what was sent**, and
`discovery.search_runs._search_source` records a complete-but-warned page as a
`SourceFailure` with `incomplete=False`. The cursor still reads `exhausted` (the slice
genuinely was searched); the failure entry is what stops `failures: []` from certifying a
degenerate query as a real absence. Contract tests drive a recorded Atom feed for the
multi-term case and assert the outgoing `search_query`.

`research discover`'s own output improves without a CLI change: the line that read
`1 page(s), exhausted   failures: []` now carries the `zero_result_query:` entry that says
which five clauses were sent.

### F4 · arXiv-id extraction and the year that came from a v3 banner

`ingest.identity.normalize_arxiv_id` / `arxiv_base_id` now **extract** `2304.09513v3` (or
old-style `cs/0101001`) from any string and return `None` when there is no identifier in it,
instead of lowercasing prose into a key that can never match. New `arxiv_year` decodes the
id's `YYMM`.

Three rules follow, each with a test:

- `ingest.metadata.find_arxiv_banner` parses `arXiv:2301.01234v3 [cs.CR] 12 Mar 2025` into
  id, version, category and stamp date, and the candidate's **year comes from the id, not
  from the date beside it** — the specific defect that put a 2023 paper into the corpus
  as 2025.
- Identity resolution prefers the id-derived year whenever the stated one contradicts it.
- A title match tolerates ±2 years once the author lists agree (`YEAR_TOLERANCE_WITH_AUTHORS`);
  a year mismatch adds no reason of its own and never defeats a DOI or arXiv identifier match.

`manuscript/support.py` is **not** this agent's module: its `_entry_arxiv` fallback is fixed
for free by the extraction change, but the strict `works[work_id].year == year` filter in
`_candidates_for` is still there and should adopt the same ±2-with-authors rule. That is the
one remaining piece of F4.

### F5 · discovery metadata that was found and thrown away

Nothing was ever lost on disk — a `SearchCandidate` persists the whole `WorkCandidate` a
source reported — it was simply never read back. So the fix is a read and a write, not a
schema change:

- `DiscoveryService.enrichments(run)` returns a `MetadataEnrichment` per candidate that
  resolved to a corpus Work and has something to offer: `fields` maps a Work field to the
  `IdentifierField`s the sources reported (field-level provenance kept), and `conflicts`
  records every disagreement. A field is proposed when the Work holds nothing for it or
  holds something `parsing.quality` calls undecodable; a readable disagreement is recorded
  and left alone unless `only_empty_or_undecodable=False`.
- `apply_enrichments(ctx, run, *, only_empty_or_undecodable=True)` writes it through
  `work.update_metadata`, resolved by name from `CAPABILITY_HANDLERS` at call time (a
  module-scope import back into `capabilities/` would be a cycle). When that capability is
  absent the plan comes back `applied=False` with `missing_capability` naming it and the
  proposed `Work` objects in hand — withheld visibly, never dropped.

For the session's own case: the OpenAlex authors and venue for W0001 are proposed, the
mojibake author list is reported as a conflict flagged `existing_is_undecodable`, and the
decodable title that already agrees is left exactly as it is.

### F6 · parse diagnostics that were recorded and never shown

### F10 · snowball seeds manufactured from reference fragments

### F9 · inclusion reasons — blocked on the domain

declared instead, reports the same, which is what shows the *flag* is doing the work rather
than the wording. The two `traffic.metrics` conflicts survive both because `_numeric_clash`
is tested before multi-valuedness is ever consulted, so declaring a numeric field
multi-label costs no real disagreement. Without any schema the queue still reports six,
which is the honest answer for a candidate that records its field's name and not the
contract that asked it.

`InterrogationSchema.fingerprint()` moves, as expected. No test pinned a literal value, and
the change is the intended one: what counts as a conflict for a field is part of the

#### F8 · showing 20 of 39

The header now reads `showing 5 of 12 item(s) — use --limit 0 for all` whenever a page is
shorter than the queue, the footer names `--limit 0` again, and `--limit 0` prints
everything. `--json` carries `shown` and `limit` beside `count`, which is the half that
misled a script rather than a person.

#### F11 · the docstring that promised a gate

`research review candidate --help` now says what the command does: it is the researcher
acting in person, so it accepts any tier including an interpretive one — that is what a
review gate is *for* — and what it refuses is an actor that is not the researcher. The
conditions belong to `research review batch`, and the help points at it.

#### F12 · one command, with the source beside it

`research review candidate <id>` **with no action flag prints the item**: verdict, anchor
status, the verifier's discrepancies and rationale, competing candidate ids, any accepted
Evidence at the same span, the quoted text, and the block it came from with its neighbours.
It changes nothing. `research review next` prints the top of the queue in Product §24.2
order with the same detail and says how many are left, so the loop is `next`, act, `next`.
Both read through `build_inbox`, so what `inbox` lists and what `next` shows cannot drift.

#### F17 · the model row that was missing rather than empty

`research egress` always prints a model row. With no `providers:` entry it reads
`(none configured — model stages will refuse)` and a line below names the commands that
will refuse and the offline alternative. `--json` carries `model_providers_configured`,
asked *before* `--denied` narrows the table — "no model row survived the filter" and "no
model provider is configured" are different facts.

#### F19 · naming a set of fields

`--field` splits on commas and still repeats, so `--field dataset,baseline`,
`--field dataset --field baseline`, and a mixture all mean the same thing. `--except-field`
is the "all fields except" half, with the same shape. Both are resolved against the schema
*before* a backend is chosen, so a mistyped field is refused by name rather than by "no
model providers configured", and excluding every field is refused rather than silently
asking nothing.

#### F20 · `research shell`

The report offered two fixes; this is the second. `research shell` keeps one process alive
and dispatches each typed line through the same Typer application in the same standalone
mode a terminal uses, so every command prints and refuses identically — it is a loop around
the entry point, not a second entry point. `-w` once covers the session. Measured on this
machine: **ten commands cost 8.4 s separately (838 ms each) and 0.9 s in a shell (90 ms
each)**, which is the 80-of-90-seconds the review loop lost.

Trimming the import cost itself — the report's first option — is not done, and is worth
saying precisely. `research --version` is ~0.79 s, of which ~0.29 s is
`capabilities.context` pulling `capabilities/__init__` and with it the projection layer and
SQLAlchemy, and ~0.13 s is `research_harness.domain.base` pulling the whole `domain`
package. Both are package `__init__` re-exports rather than anything a command needs at
import time, and unpicking them touches `capabilities/`, `domain/`, and all eleven command
modules at once. It wants its own change.

### Beyond the friction log

Three things this batch changed that the log did not name, recorded here because they alter
behaviour a reader of §13 would otherwise not expect:

- **Egress is now enforced on the server path at selection.** `capabilities/extra_handlers.py::_router`
  carried the workspace policy onto the router, but `ModelRouter` only refuses when
  `select()` is called — and `work.interrogate` answers with a run id and routes on a worker
  thread, so a refusal reached the researcher as a failed run record rather than as the
  policy that stopped it. `ModelRouter.egress_refusal()` asks the question without a request,
  and `_router` raises it before the run starts. `tests/contract/capabilities/test_server_egress.py`
  drives the registry, the daemon, and the MCP bridge over an `httpx.MockTransport` that
  fails the test if it is touched.
- **Traces are written on the server path.** `TracingRouter`, `traced`, and
  `trace_writer_for` moved from `cli/providers.py` to `privacy/traces.py` (the old names
  still import from `cli.providers`), and `_router` wraps its router in one, so a run started
  over HTTP or MCP records what it asked under `.research/traces/` with the project's
  `redact_traces` honoured as the trace is written. `claims.audit.trace_sink_for` forwards
  the sink to `cross_verify`, which calls providers directly and was the one call in a run
  that left no record.
- **Hosts can read discovery runs.** `search_run.list` and `search_run.get` are `read`
  capabilities; `search_run.get` returns the run with its candidates and the
  `MetadataEnrichment` proposals F5 made readable, naming `work.update_metadata` as what
  applies one. Until now the CLI was the only surface that could show a researcher the
  proposal it is asking them to approve.

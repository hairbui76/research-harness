# Dogfood session — the conversation-first loop (v1.1)

**Date:** 2026-09-03 · **Track:** ROADMAP Phases 18–21 and the Design System foundation ·
**Gates:** DS, P18, P19, P20, P21
**Workspace:** `/tmp/dogfood-v11`, built by `research demo` (not committed) ·
**Benchmark corpus:** `/tmp/graphbench`, `--scale 1.0` (not committed)

The v1.0 dogfood ([`dogfood-2026-09-03.md`](dogfood-2026-09-03.md)) ran a real review on
real papers. This one runs the *new* loop — chat, attachments, references, manuscript — end
to end through the shipped CLI, on the bundled demo corpus, with a real LaTeX engine.
Everything below happened; nothing was staged for the report.

Every command is timed with `time`, and every number is wall clock on the machine described
in [`performance-budgets.md`](performance-budgets.md) (Linux 5.14 x86-64, 28 CPUs, Python
3.12.13, local SSD) **while three other engineers were running test suites on it**. About
0.65–0.75 s of every CLI figure is interpreter start-up (v1.0 friction F20; `research shell`
amortises it), so the interesting number is usually the one the command prints itself.

## 2. The conversation loop

```console
$ research chat new "v1.1 dogfood: reading the demo corpus"        # 1.13 s
CS0001  private  v1.1 dogfood: reading the demo corpus
```

The first send **failed**, and it failed usefully:

```console
$ research chat send CS0001 "What does this corpus actually contain, and what is accepted?" \
    --script script.json                                            # 1.01 s
M0002  failed  (context CP0001)
error: model output was not valid JSON: Expecting value: line 1 column 1 (char 0)
```

The script was a JSON list of plain strings; a chat reply has to be `{"text": "…"}` (F1).
What the product did with the failure is exactly what the spec asks for: the transcript kept
the user's message, kept a *failed attempt record* carrying the provider error, and left the
message retryable.

```console
$ research chat retry M0002 --script script.json                    # 0.90 s
M0003  succeeded  (context CP0002)
The demo corpus holds one Work, W0001, with three verified proposals: …

$ research chat show CS0001                                         # 0.80 s
M0001  user       What does this corpus actually contain, and what is accepted?
M0002  assistant (incomplete)   (no text)      context: CP0001
M0003  assistant  The demo corpus holds one Work, W0001, …           context: CP0002
```

The failed attempt is still there. A retry is a new message, not a rewrite.

**The receipt.** With nothing accepted yet, the pack was policy + the current session. After
accepting one candidate through the ordinary v1.0 review path
(`research review candidate cand_4590… --accept` → `E0001`, 0.88 s), the same preview shows
the accepted object entering **above** the session, which is the ordering rule made visible:

```console
$ research chat context CS0001 --text "Does the dataset evidence support a corpus-level claim?" \
    --ref E0001                                                     # 0.81 s
CP0000  none  243 tokens of 8000

included:
  [policy] policy://conversation/task                    private   143 tok
  [accepted_state] rh://evidence/E0001                   accepted   17 tok
  [current_session] rh://session/CS0001?message=M0001    private    17 tok
  [current_session] rh://session/CS0001?message=M0003    private    66 tok
```

Reading a receipt that was *recorded* rather than previewed was not possible when the
session began — the pack was on disk at `conversations/CS0001/context/CP0002.json` and no
command printed it. **Fixed mid-session by parallel work**: `context.get` and
`research chat context --pack CP0002` landed while this report was being written, and the
recorded receipt now reads back through the same command (F2).

**What blocks a send.** The demo's empty `providers:` list made `attachment check` refuse
outright (F3), so two entries were added by hand — a text-only local model and a
vision-capable OpenAI entry:

```console
$ research attachment check CS0001                                   # 0.97 s
model  local/qwen2.5-7b-instruct
ok      SA0001  omitted   A0001-1.pdf         the attachment is in_corpus, not ready
BLOCKED SA0002  omitted   synthetic_two_column_paper.pdf
          the selected model does not accept application/pdf input
BLOCKED SA0003  omitted   tiny.png
          the selected model does not accept image/png input
```

No compatible-model suggestion appeared, and it took reading `_suggest` to see why: both
attachments are **private** (they inherit the private session), and the only model that
would accept them is external, so suggesting it would be suggesting an egress the policy
forbids. Correct, and invisible (F4). In a `project`-visible session the suggestion is
there:

```console
$ research chat new "shareable session" --visibility project
CS0002  project  shareable session
$ research attachment add CS0002 tests/fixtures/attachments/tiny.png
SA0004  tiny.png  image/png  196 bytes  [ready]   visibility  project
$ research attachment check CS0002
BLOCKED SA0004  omitted   tiny.png
          the selected model does not accept image/png input
          try vision/gpt-4o-mini
```

One more thing fell out of a mistyped script file: the **sendability check gates
`session.send`, not just `attachment check`**. With two unsupported attachments still in the
session, the send refused before anything was assembled:

```console
$ research chat send CS0001 "role check" --script role-keyed.json
error: session.send: 2 attachment(s) cannot be sent to scripted/scripted-1: SA0002
synthetic_two_column_paper.pdf: the selected model does not accept application/pdf input;
SA0003 tiny.png: the selected model does not accept image/png input
```

That is Gate P19 clause 3 arriving unrequested, from the CLI, on a message that had nothing
to do with attachments.

## 8. Friction log

### F1 · Medium-High · `chat send --script` needs `{"text": …}` and the error does not say so

A JSON list of plain strings is the obvious shape — it is what
`research interrogate --script` accepts for a single-reply role — and for chat it produces
`model output was not valid JSON: Expecting value: line 1 column 1 (char 0)`, which
describes the symptom, not the fix. The `--script` help says "JSON replies for the
in-process scripted provider" and names no shape.
The role-keyed shape does not rescue it either. `session.send` runs the role
`conversation`, which is *not* in the role registry, so `{"conversation": [{"text": "…"}]}`
fails `_is_role_keyed`, is read as a single reply object, and fails with a second confusing
message:

```console
$ research chat send CS0001 "role check" --script role-keyed.json
M0005  failed  (context CP0003)
error: model output did not satisfy ChatReply: 1 validation error for ChatReply / conversation
```

So exactly two shapes work for chat: `{"text": "…"}`, or a list of them.
**Suggested fix:** name the expected object in the error and in the option help
(`a chat reply is {"text": "…"}`), accept a bare string as `{"text": …}`, and either
register `conversation` as a role or say in the help that the role-keyed shape does not
apply to `chat send`.
**Cost here:** two failed messages, both of which the product handled correctly — the
transcript kept each failed attempt and stayed retryable.

### F2 · Medium · a recorded receipt could not be read back — **fixed mid-session**

`research chat context` previewed a *new* pack; the pack a past call actually used was on
disk and had no command. The plan had already recorded this as the `context.get` gap, and
it landed during the session: `research chat context CS0001 --pack CP0002` now prints the
recorded receipt, and `research providers list` (the other planned read) prints the model
catalogue a client needs for a model selector.

### F3 · Medium · `research demo` writes `providers: []`, so the demo cannot check a send

`attachment.check_send` refuses without a `providers:` list, correctly — it has nothing to
check against. But the workspace the product hands a new user for exploring is exactly the
one that cannot run the check, and the flow the attachments spec is proudest of
(block the send, name a compatible model) is therefore invisible in the demo.
**Suggested fix:** have `research demo` write two commented-out example entries, or a
disabled `local` entry, so `attachment check` has something to answer with.

### F4 · Low-Medium · a private attachment gets no model suggestion, and no reason

`_suggest` skips any external endpoint for a `private` attachment — right, because
suggesting it would be suggesting a forbidden egress. The refusal prints the per-item
reason and simply omits the "try …" line, so the researcher sees "no model can take this"
where the truth is "no *local* model can take this, and this attachment may not leave the
machine".
**Suggested fix:** when a suggestion was suppressed by privacy, say so
(`no local model accepts image/png; vision/gpt-4o-mini would, but this attachment is private`).

### F5 · Medium · `manuscript build` does not take the `latest` / `last-good` aliases

`GET /manuscript/builds/{id}/pdf` accepts `latest` and `last-good`, and the CLI's
`BUILD_ID` argument does not:

```console
$ research manuscript build last-good
error: no manuscript build last-good
```

Two surfaces of one idea disagreeing about how to name the same two questions. `build` with
no argument gives the latest, so only `last-good` is genuinely unreachable — and it is the
one you want after a failure.
**Suggested fix:** accept both aliases in the CLI argument, as the route does.

### F6 · Medium · accepting a candidate leaves the projection stale until a rebuild

Not v1.1 — nothing in this track touched the review path — but it fires in the middle of
the v1.1 loop and is two commands to reproduce:

```console
$ research demo /tmp/probe && research doctor -w /tmp/probe
[ok  ] projection        research.db agrees with canonical state
$ research review candidate cand_4590b9b1f474d343 --accept -w /tmp/probe
$ research doctor -w /tmp/probe
[FAIL] projection        2 discrepancy(ies), run `research rebuild`: evidence: 1 canonical
                         object(s) not projected: E0001; events: 1 …
```

A normal, correct acceptance turns the workspace's own health check red until the
researcher runs `research rebuild`. The canonical state is right and the projection is
behind, which is the documented direction of drift (ADR-001) — but `doctor` reports it as a
`[FAIL]`, which reads as "something is wrong" rather than "the index is one write behind".
**Suggested fix:** either upsert the accepted object into the projection inside the same
capability, or have `doctor` distinguish "the projection is behind canonical state" from
"the projection disagrees with canonical state".

### F7 · Low · the generated CLI reference silently rewrapped to 80 columns

`docs/guide/gen_cli_reference.py` pins `COLUMNS=88` and `TERM=dumb`, but rich treats a
`dumb` TERM as an 80-column terminal *and ignores `COLUMNS`* whenever it also believes it
is writing to a terminal — which `FORCE_COLOR` in the environment is enough to make it
believe. Regenerating from a shell that exports `FORCE_COLOR` (several agent and CI runners
do) rewrote all 1,796 lines of `cli-reference.md` at 80 columns: a 1,022-line diff with no
CLI change behind it.
**Fixed in this session:** the generator now pops `FORCE_COLOR`, `CLICOLOR_FORCE`, and
`TERMINAL_WIDTH` before importing click, so the page's width depends on the file and not on
whose shell ran it.

### F8 · Low · an accepted candidate is still projected as a candidate

After accepting `cand_4590…` into `E0001`, `research graph complete E` lists both
`E0001 [evidence/accepted/project]` and `candidate:cand_4590… [evidence/candidate/project]`
with the same text. Both rows are true — staging still holds the candidate, and the labels
differ — but a composer's `@` menu shows the same sentence twice.
**Suggested fix:** none required; if it becomes noise, autocomplete can drop a candidate
whose acceptance produced an object it also lists.

## 9. What worked well

- **The failure path was the best-behaved part of the session.** The one thing that broke
  (F1) left a durable transcript, a failed attempt record with the provider's message, and
  a `retry` that produced a new message without touching the old one. Nothing had to be
  cleaned up by hand.
- **Ordering as a mechanism, not a promise.** Accepting one Evidence object was enough to
  see it enter the pack above the session messages, in the receipt, with its authority
  printed. No configuration made that happen.
- **`rm -rf .research/` is still safe, and now it is safe for chat too.** Transcripts,
  attachments, and receipts survived; search and `show` kept working with no index; the
  rebuild reproduced the same canonical digest and resolved the same references.
- **Real compilation is genuinely fast.** 0.38 s for a three-file document with `tectonic`,
  with the PDF, the log, the SyncTeX map, and a `build.json` all landing under
  `.research/build/manuscript/<id>/`.
- **The two lists never merged.** Across a clean build, a broken build, and a re-read of a
  build, compiler diagnostics and audit findings stayed separate and were never summed.
- **The suggestion boundary held under a hostile test.** The file hash was unchanged after
  staging a diff; applying against a wrong hash was refused with the two hashes printed;
  applying for real recorded a `manuscript.source_written` event.
- **The graph budgets are not close.** Three orders of magnitude of margin on the
  interactive modes, on a shared machine, on the agreed corpus.
